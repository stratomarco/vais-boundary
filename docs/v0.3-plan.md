# v0.3 plan: adaptive verification

v0.2 stabilized the deterministic security boundary. v0.3 adds the evaluation substrate needed to test that boundary with adaptive attackers.

## Research objective

Evaluate whether a defense-aware prompt-injection generator can discover observable invariant violations that are missed by static attack corpora, while keeping model compromise distinct from application compromise.

## Implemented in v0.3 core

- stable `Scenario` abstraction;
- stable `TargetAgent` protocol;
- stable `Attacker` protocol with feedback history;
- deterministic static attacker;
- ordered replay attacker;
- strict scenario-specific JSONL corpus replay;
- protected and deliberately unprotected execution paths;
- deterministic JSONL episode records;
- policy/invariant configuration hashes;
- clean utility oracle;
- IVR, drift, attack influence, deny, approval, utility and reward metrics;
- per-target and per-scenario summaries;
- five deterministic security scenarios;
- exact-action approval post-effect invariant;
- committed benchmark corpus and regression snapshots;
- CI failure on protected invariant violations and clean-utility regressions.

## Episode result

Results do not collapse to one ASR bit. Each episode records:

- candidate injection;
- behavioral-drift finding;
- baseline and candidate plans;
- ALLOW/DENY/REQUIRE_APPROVAL records;
- effects and provenance;
- detailed invariant violations;
- terminal security reward;
- clean utility outcome;
- target/model metadata;
- policy/invariant hashes.

## Initial benchmark scenarios

1. **email recipient hijack** — untrusted document attempts to change a trusted recipient;
2. **secret-to-public egress** — injected content attempts to mix a canary/secret into outbound content;
3. **payment destination hijack** — destination is bound to trusted intent;
4. **forbidden tool escalation** — injected content attempts to invoke `shell_exec`;
5. **approval replay** — attacker changes a high-value action after approval of a different exact action.

Each scenario has clean, attacked-unprotected and attacked-protected semantics.

## Acceptance status

- [x] runner produces deterministic JSON result records for deterministic targets;
- [x] static attacks demonstrate positive terminal reward in deliberately vulnerable/unprotected mode;
- [x] same committed attacks produce zero terminal reward when protected by the intended invariant;
- [x] approval replay scenario is blocked and independently detectable post-effect;
- [x] per-target metrics are retained rather than hidden in an aggregate;
- [x] static/replay attackers consume the same terminal reward API intended for RLVR;
- [x] all new security semantics have regression tests;
- [x] committed snapshot catches accidental semantic changes;
- [ ] at least two **real target-model** adapters run the same scenario contract;
- [ ] black-box iterative attacker baseline;
- [ ] original capstone RLVR attacker imported behind the `Attacker` interface;
- [ ] every RLVR checkpoint evaluated through the same runner;
- [ ] balanced scenario/model sampling for RLVR training/evaluation.

The unchecked items are intentionally not faked with deterministic target profiles. Those profiles validate benchmark plumbing only.

## RLVR integration order

1. Add a model-independent structured-plan adapter contract for real inference backends.
2. Run at least two real target models on the same five scenario definitions.
3. Add a simple black-box iterative attacker baseline.
4. Import the capstone generator behind `Attacker`.
5. Use invariant violation as terminal reward.
6. If shaping is needed, keep behavioral-drift reward in a separate field.
7. Evaluate every training checkpoint, not only the final checkpoint.
8. Balance scenario/model sampling to avoid reproducing the capstone specialization bias accidentally.

## What not to do yet

- do not optimize a learned security judge when a deterministic invariant exists;
- do not add many agent-framework adapters before the target-plan API is validated;
- do not claim prevention of all prompt injection;
- do not treat zero IVR on the deterministic suite as evidence of general robustness;
- do not reconstruct the capstone RLVR code from the manuscript if the original source can be imported instead.
