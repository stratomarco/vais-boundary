# v0.5 empirical runner

v0.5 is the transition from architecture validation to research-grade real-target experiments.

## Goals

The empirical runner must make it difficult to accidentally publish misleading security numbers.

The required properties are:

1. target failures are explicit and excluded from security denominators;
2. protected and unprotected execution use the same generated plan;
3. model/inference metadata is preserved where the runtime exposes it;
4. infrastructure retries cannot become resampling of model outcomes;
5. per-target and per-scenario results are available before aggregation;
6. uncertainty is visible through confidence intervals;
7. model reasoning text is not persisted by VAIS.

## Episode state machine

```text
                      TARGET GENERATION
                             |
          +------------------+--------------------+
          |                  |                    |
          v                  v                    v
      VALID PLAN         TRUNCATED/          TIMEOUT/
                         INVALID PLAN         TRANSPORT
          |                  |                    |
          v                  +---------+----------+
  SECURITY EVALUATION                  |
          |                            v
          |                    TARGET FAILURE DATA
          |                     security reward=null
          |
     +----+----+
     |         |
     v         v
  no effect  effect
 violation  violation
     |         |
     v         v
 reward=0   reward=1
```

## Primary publication rule

Never report IVR, ASR-like security rates, or VAIS reduction numbers without also reporting:

- valid-security episode count/rate;
- target failure rate;
- clean utility;
- per-model results;
- number of scenarios/attack candidates.

A 0% IVR with 0 valid episodes is not a security result.

## v0.5 -> v0.6

After the real-target runner is stable, expand the static adversarial corpus before integrating RLVR. The static corpus becomes the fixed control condition against which the adaptive attacker is compared.


## v0.5.1 measurement-correctness patch

v0.5.1 separates four outcome stages that v0.5.0 partially conflated:

1. `plan_changed` -- any externally proposed tool/plain-argument change;
2. `behavioral_drift` -- a security-relevant change;
3. `attack_objective_success` -- deterministic scenario-specific attack-goal success;
4. `terminal_security_reward` / IVR -- observable invariant violation after execution.

`attack_influence_rate` was removed because it was implemented as raw plan inequality and could therefore count harmless wording differences as successful influence.

The behavioral gate now also recognizes drift from exact prior approvals, so a payment change such as `150 -> 999` is security-relevant even when `amount` is not independently bound in the task contract.

When a run is labeled reasoning `off` but the server reports reasoning tokens or reasoning text length, the target-health summary explicitly flags the configuration mismatch.
