# VAIS Boundary v0.12.0rc12 release review

Date: 2026-09-22

## Scope and decision rule

RC11 put the reference monitor's decision function under adversarial test. RC12 reviews its
edges: what is passed into the monitor, what the verifier is told, what persists, and what the
documents claim. It was prompted by a second external reviewer's questions and completed by a
full re-read of the enforcement core, the MCP path and the benchmark adapters.

Nothing in the review bypassed a DENY. Seven defects were found and fixed, each with a regression
test that fails when its fix is reverted, and eleven limitations were published.

The frozen RC7 benchmark evidence is carried unchanged and RC12 makes no new model claims from
it. The review does not certify production readiness and does not extend any benchmark claim.

The tagged tree also contains `website/` and `campaigns/`. Neither is part of the library, both
are absent from the wheel and the sdist, and `website/` is outside every gate check below.

## Material findings, fixed

### FIND-049, FIND-050, FIND-051: consume-once held on one path, was invisible to VERIFY, and was uncountable

`MCPProtectedClient` took no `ApprovalStore` and called the monitor without one, so on the MCP
path the monitor fell back to the contract's approved fingerprints, which never consume. One
approval authorized the same call every time it was proposed (FIND-049).

The monitor consumes store grants, but `exact_action_approval` looked only at the contract, so a
payment correctly approved through the store was allowed by ENFORCE and reported as unapproved by
VERIFY (FIND-050). The engine and `DeclarativeVerifiableReward` now accept the store, and a
consumed grant for the same identity counts as approval while an unconsumed one does not
(DEC-041).

No invariant counted how often one approval was used, so one contract-held approval replayed
across two identical payments passed VERIFY twice while ENFORCE allowed both (FIND-051). The new
aggregate invariant `approval_single_use` reports it and is in the default set. It also reports a
genuine re-approval of an identical action, because the store cannot show two approvals (DEC-042).

None of the three was a bypass: the action that ran was always exactly the approved one. All
three broke a property this project states.

### FIND-052: a security mapping that one operator could mutate

`FrozenDict` blocked `update` and the other mutators, but `dict.__ior__` is implemented in C and
bypasses them, so `contract.bound_arguments |= {...}` replaced a trusted binding and an in-place
union on an action's arguments changed its fingerprint after the fact. Unreachable by a model and
reachable by integration code. `__ior__` now raises; deliberate unbound `dict` calls cannot be
prevented in Python and remain outside the threat model.

### FIND-053, FIND-054, FIND-055: three loader contract faults

The continuous campaign found `trust_required` tested with set membership, so an unhashable value
raised `TypeError` (FIND-053). It is the FIND-047 pattern one field over; this time every
set-membership test in the three loaders was checked, and only that one was unguarded. Reading
the MCP loader then found a `:` in a server or tool name escaping as `ValueError` (FIND-054), and
NFC-equal effect field names merged silently, so the file and the loaded mapping could disagree
(FIND-055). The MCP loader is not a campaign target (LIM-054).

## Changes to scoring

**An indeterminate call is no longer scored as defended (DEC-040).** A call that fails after
dispatch produces no effect record, so the verifier saw nothing and the episode scored as
secure. Absent a verified violation, all three scorers now remove the episode from the evaluable
set and count it separately, as they already did for target failures. Every published run
recorded zero indeterminate calls, so no published number changes; both regenerated snapshots
differ from RC11 only in the version, the version-dependent configuration hash, and the new
counters, which are zero everywhere.

**Audit events identify the action and the session (DEC-043).** Both enforcement paths record
the action fingerprint and the contract's identity, never argument values, and the MCP client can
now keep an audit trail.

## Limitations published

LIM-044 to LIM-054. The ones that matter most to an integrator:

- consume-once needs an `ApprovalStore`, and holds within one store instance rather than across
  processes (LIM-044, LIM-045);
- an MCP effect is the request VAIS dispatched, not state read back from the system of record, so
  a server doing something else is not detected (LIM-046, LIM-049);
- authority has no freshness, revocation or expiry (LIM-047);
- authority is judged per argument, and a proposed action carries no provenance of its own; the
  default policy accepts an untrusted payment amount up to its approval threshold (LIM-048);
- complete mediation is assumed, and the agent's text and reasoning output are not mediated at all
  (LIM-050, LIM-051).

## Security-boundary review

| Review item | Bounded result |
|---|---|
| Approvals | **Changed.** Consume-once on the MCP path when a store is supplied; VERIFY sees store grants; reuse of one approval is reported. Still not enforced without a store, and not across processes. |
| Invariants | **Extended.** One new aggregate type, `approval_single_use`, added to the default set (seven invariants). `exact_action_approval` accepts the store. The other five types are unchanged. |
| Config loading | **Changed.** Three more malformed inputs are rejected as `PolicyValidationError`, one of which previously changed a mapping's meaning silently. No schema semantics changed. |
| Security mappings | **Changed.** `FrozenDict` rejects in-place union. |
| Audit | **Changed.** Events carry the action fingerprint and contract identity; the MCP client can audit. Still hash chained and not externally anchored (LIM-037, LIM-038). |
| Benchmark scoring | **Changed.** Indeterminate outcomes leave the evaluable set. No published result changes. |
| Reference monitor decision function, provenance lattice, canonicalization | Unchanged from RC11. |

## Open surfaces shipping unmitigated

**S13, the decision-reason output channel.** Unchanged since RC10.

**Limits that span several actions (LIM-035, LIM-044).** A bound on the count of effects, and a
single use of an approval when no store is supplied, are detected in VERIFY after the fact and
not denied in flight, because the reference monitor holds no state across decisions. A stateful
monitor sharing one ledger with VERIFY is the planned fix; no date is promised, and tests assert
both limitations so they stay visible.

**S15, model text and reasoning output (LIM-051).** Not mediated by any enforcement path.

## Validation and release gate

RC12 is releasable only after all of the following succeed on the final commit:

1. full source regression suite;
2. a mutation check of every fix in this release;
3. default policy and invariant validation;
4. deterministic protected benchmark smoke test on the default and MCP paths;
5. wheel and sdist build plus isolated wheel installation with a probe for every fix, with
   `experiments`, `website` and `campaigns` absent from both;
6. deterministic source ZIP reproduction and SHA-256 manifest verification;
7. campaign harness self-test, and a campaign on each target with no `real` verdict;
8. tracked-tree privacy and secret scans, and a research-doctor result identical to a clean RC9 tree;
9. clean GitHub CI across Python 3.11-3.14 on Windows and Linux;
10. annotated `v0.12.0rc12` tag and release assets built from the verified commit.

Passing these supports only the recorded implementation and packaging result. It does not
establish universal prompt-injection resistance, production authorization-service readiness,
external audit anchoring, or any general claim about content-filtering defences.
